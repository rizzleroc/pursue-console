# Coverage Wall — live data bindings

Every visible value on the new LIVE-view Coverage Wall (and on the
existing dashboard panels the design preserves) maps to a JSON file in
`public/`, and every JSON file is regenerated by a script in
`scripts/` that runs as part of `npm run build`. Nothing on the page
is hard-coded.

This file is the contract. If you add a new value to the UI, add a row.
If a row's "JSON source" doesn't exist, you've created an unbound
value — don't ship it.

## The pipeline

```
data lands  →  npm run build (19 scripts in order)  →  public/*.json
                                                    ↓
                                          React hooks fetch with
                                          60s revalidate + cache
                                                    ↓
                                          UI updates next paint
```

The deployed site (`https://rizzleroc.github.io/pursue-console/`) is
rebuilt on every push to `main` via `.github/workflows/deploy.yml`. A
scheduled FAISS rebuild also runs nightly. So "live" means
**corpus-fresh-on-build**, not WebSocket-live. A user with an open tab
catches the next build inside 60s (see hooks below).

## React hooks (the binding layer)

| Hook | Reads | Cache pattern |
|---|---|---|
| `useCorpusStats()` | `corpus-stats.json` | module-level promise · 60s revalidate · 800ms backoff retry |
| `useCoverage()` (new) | `coverage.json` | same |
| `useNextMissing()` (new) | `next-missing.json` | same · also returns `top` for CTA binding |
| `usePatterns()` (new) | `patterns.json` | same |

All four hooks follow the identical signature `{ data, error, reload }`
so consumers can swap or combine them without surprises.

## Build chain — current order (post-PR-265)

`npm run build` runs 21 scripts in series. The new additions:

```
… build-work-available
+ diagnose-coverage          ← writes public/coverage.json
+ build-next-missing         ← writes public/next-missing.json
… extract-media-from-gemini
…
```

`diagnose-coverage` must run **after** `build-work-available` because
the coverage status uses the per-event work counts. `build-next-missing`
must run **after** `diagnose-coverage` because it scores candidates
by coverage gaps.

## How to verify a row

For any row in the tables above:

1. Look at the listed JSON source under `public/`.
2. Inspect the value via `node -e "console.log(require('./public/X.json').Y.Z)"`.
3. Confirm the rendered UI value matches.
4. If you changed the underlying corpus and re-ran `npm run build`,
   the rendered value should change without any code edit.

The contract is: if step 4 fails, the row is broken — either the
script doesn't write what the docs say, or the UI hard-codes
instead of binding. Open an issue.
